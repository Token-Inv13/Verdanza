# Parrainage V1 — backend inert-first

Version commerciale figée : `referral-commercial-policy-v1`. Le parrain reçoit 1 000 centimes, le filleul obtient 500 centimes de remise, et la base de produits éligibles avant cette remise doit atteindre 5 000 centimes. Aucun calcul monétaire ne repose sur des euros flottants.

## Ouverture et sécurité

Sans configuration, `GET/POST /api/referral` renvoie `503 referral_program_disabled` avant Auth, Firestore ou le secret HMAC. `REFERRAL_PROGRAM_MODE=off` seul a le même effet. Toute configuration partielle ou inconnue échoue fermée. `active` et `drain` exigent `REFERRAL_RUNTIME_ENVIRONMENT=production`, `VERCEL_ENV=production`, `REFERRAL_STARTS_AT_EPOCH_MS` entier, `REFERRAL_PROGRAM_VERSION=referral-commercial-policy-v1` et le projet Firebase Admin exact `verdanza-1f621`. `drain` permet uniquement la lecture propriétaire et l’achèvement/correction des commandes dont le snapshot existe ; il bloque la création de code ou de lien. Les tests injectent une configuration locale explicite aux services : aucune variable Vercel Preview ne peut ouvrir le programme.

`REFERRAL_EMAIL_HMAC_KEYRING_JSON` est une configuration serveur stricte de forme `{ "activeVersion": "v2", "keys": { "v1": "…", "v2": "…" } }`. Chaque secret comporte au moins 32 octets UTF-8, quatre versions au maximum sont acceptées, et toute version active manquante ou inconnue échoue fermée. La clé n’est lue ni au démarrage ni en mode `off` ; elle sert au lien et à la revalidation d’tout paiement produits authentifie sous un runtime opérationnel. Chaque ID de claim est un HMAC-SHA256 séparé par domaine et version de l’email normalisé. Les alias de toutes les clés retenues, y compris l’ancien ID non versionné `v1`, sont lus dans la transaction avant de créer le claim de la version active. Conserver les anciennes clés tant que **tous** leurs claims ne sont pas migrés ; ce lot ne migre aucune donnée Production. Le secret, le HMAC et l’email ne sont jamais envoyés dans `GET self` ni loggés. `GET self` ne révèle aucun code partageable ; `POST ensure_code` vérifie l’éligibilité du parrain avant de le rendre. Les collections et les événements d’audit sont interdits au SDK client par les règles candidates ; leur déploiement relève d’un gate distinct.

Avant la création ou la récupération d’un code, puis avant un lien, l’identité du parrain est relue par l’API Auth Admin `projects.accounts:lookup` avec le jeton OAuth du credential Firebase Admin déjà initialisé. La lecture ciblée par UID a lieu hors transaction Firestore ; un compte désactivé ne crée ni code ni lien. Au premier paiement d’une commande avec snapshot, le préflight Auth relit **parrain et filleul** et lie ces faits à la relation observée. Après le contrôle historique, la transaction revalide ce binding et le claim email sous toutes les versions HMAC retenues. Un échec d’identité filleul ou un auto-parrainage refuse le paiement remisé par conflit 409 avant toute écriture ; le claim actif libre n’est créé que si le paiement est accepté. La transaction revérifie ensuite une commande parrain réelle, payée et livrée. Un parrain désactivé, indisponible ou devenu inéligible seul laisse le paiement et le claim filleul être confirmés, sans gain parrain ; le motif borné est conservé dans la relation. Cette absence de gain est définitive en V1. L’Auth n’est pas relu à la livraison d’un gain déjà pending. Une erreur de jeton ID client renvoie `401 authentication_required` ; une erreur de configuration ou d’indisponibilité Auth de ce jeton renvoie `503`.

La réservation de l’email courant vérifié est indépendante de l’attribution des 10 € au parrain et de l’existence d’une relation. Les aliases HMAC sont lus et le claim actif libre peut être créé même sans relation ou si le parrain seul est inéligible. Pour une commande remisée, le binding, les conflits de claim et l’auto-parrainage restent stricts : un refus du paiement ne laisse aucun claim ni preuve. Pour un paiement sans remise, un binding de relation changé ferme le droit commercial et invalide le certificat, mais l’identité Auth valide reste protégée par son claim et sa preuve technique.

## Documents

- `referralCodes/owner_<uid>` et `referralCodes/code_<BASE32>` contiennent le même mapping versionné. Le code comporte 128 bits aléatoires encodés sur 26 caractères Base32 majuscules. Collision et unicité du propriétaire sont vérifiées dans une transaction ; le code existant est conservé.
- `referrals/<refereeUid>` est la relation versionnée. Elle conserve le parrain, le filleul, l’état (`linked`, `pending`, `rewarded`, `cancelled`, `reversed`), l’identifiant de la commande qualifiante, les preuves paiement/livraison, le compartiment du droit, la base retournée cumulée et les identifiants de remboursements traités. Le parrain et la commande qualifiante sont figés après qualification.
- `referrals/<refereeUid>/events/sponsor_change_<revision>` conserve chaque changement explicite de parrain avant paiement, de manière append-only et dans la transaction du relink. Le replay du même code n’ajoute rien ; A→B→A conserve deux événements. Ces événements sont serveur uniquement.
- `referralEmailClaims/<HMAC>` réserve un email normalisé pour un UID. La convention `referralId === refereeUid` reste inchangée, mais un claim peut précéder tout document `referrals/<uid>` et ne crée aucun droit commercial. Aucun email clair. Un lien refuse un alias appartenant à un autre UID ; le même UID réutilise le claim sans duplication. Un paiement sans remise reste accepté face à un claim d’un autre UID, avec une preuve `protected_by_existing_claim`.
- `orders/<id>.customerEmailNormalized` est la forme canonique serveur de l’email (`String(email).trim().toLowerCase()`), distincte du `customerEmail` brut conservé pour les communications. Le payload des nouvelles commandes la persiste systématiquement ; le premier paiement d’une commande legacy la répare si absente ou incorrecte et si `usableOrderEmail(customerEmail)` est exploitable, dans la même transaction et uniquement sur cette commande. Si le brut est inexploitable, aucun normalized artificiel n’est écrit, même si un ancien normalized semble plausible. Le type reste optionnel pour l’historique. Le helper partagé sert aussi à la normalisation stricte Referral et à la migration.
- `referralMigrations/order-email-normalization-v5` certifie la migration technique exhaustive : `schemaVersion: 1`, `version: "order-email-normalization-v5"`, `status: "complete"`, `completedAtEpochMs`, `verifiedOrders`, `verifiedPaidProductOrders`, `verifiedReferralRelations`, `verifiedUnresolvedIdentityRelations: 0`, `verifiedLinkedRelationsWithPaidHistory: 0`. Les certificats V1, V2, V3 et V4 ne satisfont pas cette garantie V5. Ces compteurs entiers et l’instant positif sont validés ; aucun email ne figure dans le marqueur. Les règles candidates refusent lecture et écriture client, descendants compris. Un premier paiement produits avec email brut inexploitable invalide atomiquement tout marqueur existant : `status: "incomplete"`, schéma/version techniques imposés, `invalidatedAtEpochMs`, `invalidationReason: "paid_order_email_unusable"`, `invalidationRevision` entière incrémentée (ou 1 si invalide/épuisée), sans PII ajoutée. Même un marqueur déjà incomplet change de version Firestore ; une ancienne précondition de migration ne peut plus certifier son scan périmé. Un marqueur absent est lu transactionnellement mais jamais créé par le paiement ; une création concurrente impose la sérialisation ou le retry.
- `orders/<id>.referral` est un instantané serveur versionné : base et seuil avant remise, remise totale, allocation par ligne et empreinte. Il ne contient pas le UID parrain. Chaque ligne doit avoir une base strictement positive et conserver au moins 1 centime net après sa part de remise parrainage ; le futur allocateur checkout devra respecter cet invariant. Le checkout normal ne construit pas encore cet instantané ni la remise ; la fabrique sert à l’injection locale et au prochain lot.
- `cagnotteWallets/<sponsorUid>` et `cagnotteMovements/<eventKey>` sont le seul solde et journal monétaires. Aucun `referralRewards` n’est créé.

## Transitions et remboursements

`off` ferme les nouvelles activités Parrainage, mais les remboursements confirmés et corrections d’une relation déjà qualifiée et versionnée restent traitables après rollback. Ces deux événements de settlement ne résolvent aucun runtime environnemental, même si sa configuration est absente ou malformée : snapshot, relation, faits paiement/livraison, historique des retours et ledger persistés restent strictement validés. Ils ne créent ni lien, ni remise, ni claim ; une relation jamais qualifiée ne peut pas acquérir un droit par remboursement. Une restauration compense les faits corrigés d’un droit existant, avec replay idempotent.

La lecture affiche « Récompense de parrainage affectée à une régularisation » si un gain disponible est entièrement absorbé (`availableDeltaCents = 0` et `regularizationDeltaCents < 0`). En compensation partielle ou sans compensation, le libellé reste « Récompense de parrainage disponible ». Cette distinction de présentation conserve les montants bruts, les détails de compartiments et le ledger financier.

Le cycle de commande résout le runtime Parrainage uniquement pour un paiement avec snapshot ou `customerId`, et pour une livraison avec snapshot. Une commande anonyme sans snapshot et une simple livraison sans snapshot ne le résolvent jamais. Une configuration invalide est traitée comme fermée pour le paiement sans remise, sans lecture de relation, Auth ou keyring et sans correction Parrainage persistée ; l’historique de ce paiement interdit une remise ultérieure après réactivation. Pour une commande portant un snapshot, la même configuration invalide refuse paiement ou livraison avant toute écriture avec `503 referral_configuration_invalid`. Un runtime absent ou explicitement `off` conserve son comportement inert, y compris pour un ancien snapshot. Le runtime explicitement injecté est utilisé sans résolution environnementale.

En mode `off`, le paiement d’une commande, avec ou sans snapshot `referral`, n’attribue aucun gain et ne lit ni ne modifie les collections commerciales Parrainage ; le paiement métier continue. La maintenance technique du certificat est indépendante de ce runtime : un premier paiement produits réel avec email inexploitable lit le marker et invalide seulement un document déjà existant, même avec configuration absente, off ou malformée. Elle ne résout pas le runtime uniquement pour cette maintenance, ne consulte ni Auth ni HMAC, et ne crée ni relation, ni claim, ni wallet, ni mouvement. Les précommandes suivent le même prédicat de commande produits que la preuve historique ; fixtures et documents non produits sont exclus. En mode opérationnel, **toute première transition de commande produits vers `paid`** lit la relation du filleul dans la transaction. Si le checkout n’a appliqué aucune remise parrainage (seuil non atteint ou promotion prioritaire), un lien `linked` est consommé en `cancelled` avec `first_paid_order_without_referral_discount`, sans wallet ni mouvement. Pour une commande avec snapshot, la qualification recherche d’abord, dans la même transaction, toute autre commande produits payée historiquement par UID et, si l’email courant est vérifié, par email canonique avec variantes legacy en défense supplémentaire. Un paiement historique déjà trouvé interdit le paiement de la nouvelle commande remisée avec un conflit 409, sans mutation de la relation ; un nouveau devis sans remise est nécessaire. Un historique saturé ou incohérent refuse également le paiement remisé avec `referral_history_inconclusive` (409), avant toute mutation de commande, relation, claim, wallet ou ledger : la commande doit être requotée sans remise. Une commande sans snapshot Referral reste payable et consomme le lien sans gain. Aucune rétroattribution, tâche différée ou mutation commerciale Parrainage en mode `off` n’est prévue. La livraison prépaiement reste un fait de commande : elle ne réserve ni `qualifyingOrderId` ni `deliveredOrderId` dans la relation. La première commande réellement payée réclame la relation dans sa transaction ; si elle est déjà livrée, le paiement établit aussi sa livraison et les deux mouvements sont inscrits ensemble. `deliveredOrderId` désigne uniquement cette commande qualifiante. Une autre commande avec snapshot ne peut plus passer à `paid` après consommation du droit ; ses transitions hors paiement restent indépendantes. Une commande sans snapshot reste payable. Si le parrain reste éligible, le paiement inscrit `referral_reward_pending` et +1 000 pending ; la livraison de la commande qualifiante inscrit `referral_reward_available`, retire 1 000 pending et rend disponible le reliquat après compensation d’une éventuelle régularisation. Une annulation statutaire avant paiement ne touche pas la relation. Après paiement, le statut `cancelled` n’altère ni la relation ni le wallet parrain ; seul un remboursement confirmé sous le seuil retire le gain. Les IDs de mouvements sont déterministes et les transactions Firestore sérialisent les accès concurrents au même wallet.

Une commande portant à la fois un snapshot `referral` et une réservation ou utilisation de cagnotte positive est refusée avant les plans financiers et avant toute écriture de paiement. Un enrollment cagnotte à zéro reste compatible avec le parrainage ; une commande incompatible déjà enregistrée reste annulable selon le contrôle de paiement impayé existant. Le prochain lot checkout devra empêcher la création de ce mélange et demander un nouveau devis explicite en cas de cagnotte positive.

Pour une commande déjà remisée, l’identité filleul actuelle doit rester valide et exclusive au paiement. Un binding modifié, un compte désactivé, un email non vérifié, une identité ou un keyring indisponible, un claim détenu par un autre UID ou l’auto-parrainage provoquent un conflit 409 avec le motif précis, avant toute écriture. Un nouveau devis sans remise est requis. Une inéligibilité du parrain seul (compte désactivé, Auth indisponible ou absence de commande payée et livrée) ne retire pas la remise filleul : le paiement reste accepté et son claim courant est créé ou migré, sans reward parrain. Les commandes sans snapshot conservent leur paiement métier et leur consommation du lien sans gain.

Une commande avec snapshot `referral` et avantage commercial prioritaire effectivement appliqué est aussi refusée avant paiement : code promo (y compris livraison offerte), prix promotionnel, gain concours, promotion automatique ou cadeau. Le contrôle utilise les faits persistés (`couponCode`, `promoCode`, `promoId`, `contestPrizeId`, `promoApplied`, `promotionDiscountTotal`, `appliedPromotions`, lignes cadeau ou liées à une promotion). `discountAmount` contient potentiellement la remise parrainage et ne suffit pas à établir un conflit ; la livraison offerte sans avantage promotionnel n’en établit pas un non plus. Le checkout devra produire un devis exclusif avant toute activation.

Le remboursement confirmé et la correction administrative appellent le même service dans leur transaction. Le cumul retourné est calculé par ligne depuis l’historique des retours, puis ramené en base avant remise à l’aide de l’allocation figée et d’une division entière. Si la base retenue tombe sous 5 000 centimes, le droit pending est annulé, ou le droit disponible est contrepassé jusqu’au solde disponible ; le reste devient `regularizationCents`, sans dette financière. Une correction qui restaure le seuil émet `referral_reward_restored`, puis `referral_reward_available` si paiement et livraison sont établis. Les remboursements/corrections rejoués avec le même ID et le même cumul sont sans effet.

Le lien et le paiement remisé interrogent les commandes par UID puis `customerEmailNormalized == canonicalEmail`, indépendamment du statut courant du paiement. Les variantes exactes `customerEmail` restent une défense supplémentaire ; elles ne prouvent jamais l’absence d’historique. Une vraie commande produits, y compris une précommande, avec `paymentStatus=paid` ou un instant historique valide `paidAt`/`paymentConfirmedAt` disqualifie le filleul même après annulation, remboursement, archivage ou marquage `deletedAt`. Une précommande impayée ne consomme pas le droit ; si elle est payée après un lien en mode opérationnel, elle le consomme comme toute commande produits sans remise Referral. Les commandes annulées sans paiement, les liens envoyés et les statuts pending ne suffisent pas. Chaque requête est bornée à 100 documents et refuse un historique saturé plutôt que de supposer l’absence de commande. La canonisation couvre la casse et les espaces, sans fusionner des alias différents de messagerie.

Une preuve positive de paiement reste `found` même sans certificat. Sans preuve positive, un certificat absent, incomplet ou invalide impose `referral_history_inconclusive` : aucun lien nouveau et conflit 409 avant toute écriture sur un paiement remisé. `ensure_code` exige aussi ce certificat avant de créer ou retourner un code partageable. `GET self` reste une projection read-only sans ce gate. Une commande plain reste payable et consomme un lien opérationnel sans gain ni remise. Avec un email exploitable et une identité courante revendiquée avec succès, elle ne lit pas le certificat ; avec un email inexploitable et de vraies lignes produits, son premier paiement invalide atomiquement un certificat existant. Les refunds/corrections de droits figés ne consultent ni n’invalident le marqueur, car ils n’introduisent aucune première preuve de paiement. Le champ normalized n’est ajouté ni à l’API Referral, ni aux analytics, logs ou mouvements.

La preuve historique accepte les instants ISO avec `Z` ou offset `±HH:MM` et jusqu’à trois décimales. Le calendrier civil, l’heure et les minutes d’offset sont validés avant `Date.parse` : un décalage horaire valide ne fait pas disparaître un paiement annulé ensuite, tandis qu’une date impossible ne devient pas une preuve.

Une précommande payée en mode `off` laisse la relation et les claims inchangés. Après réactivation, son historique interdit toute autre commande remisée ainsi que tout nouveau lien ou changement de parrain. Le refus ne modifie ni la commande candidate ni la relation : aucun `qualifyingOrderId` rétroactif ni backfill n’est écrit.

Même sans snapshot, le préflight d’un premier paiement relit l’identité actuelle du filleul ; la transaction revendique son email vérifié sous la clé HMAC active s’il est libre, en conservant les anciens claims. Un email déjà revendiqué ou une identité invalide ferme la relation avec un motif borné, et le paiement reste confirmé.

## Paiement authentifié pendant Referral closed

Un premier paiement d’une vraie commande produits avec customerId sous runtime absent, off ou malformed (paiement plain) ne lit ni Auth, ni keyring, ni relation ou claim Referral. Il continue normalement et invalide atomiquement le certificat V5 existant avec le motif borné payment_identity_unresolved, timestamp et incrément de révision. Un email brut inexploitable conserve le motif prioritaire paid_order_email_unusable ; un seul plan de maintenance écrit le marker. Un marker absent n’est jamais créé. Paiements anonymes et fixtures Production sont exclus de cette invalidation conservatrice. Un snapshot sous configuration malformed reste refusé en 503 avant paiement.

La migration V5 garde seulement en mémoire interne les customerId des commandes produits historiquement payées, sans log ni projection. Elle conserve le blocage linkedRelationsWithPaidHistory et exige une preuve d’identité sûre pour chaque paiement authentifié, précommandes incluses. Un paiement closed sans relation laisse une preuve unresolved et ne peut être recertifié avant réconciliation technique puis migration exhaustive distincte. Elle n’altère aucune relation et ne crée aucun claim ou droit. Les préconditions marker empêchent la certification stale et protègent aussi le replay no-op. V1/V2/V3/V4 restent fail-closed. Aucune migration Production, même dry-run, dans ce lot.

## Réconciliation admin des faits historiques

L’action admin dédiée { reconcileReferralDelivery: true } est un booléen strict et exclusif : aucun statut, moyen de paiement, lien, note, tracking, archive/masquage/restauration, suppression ou revue impayée ne peut être combiné. Elle exige un snapshot et une preuve historique de paiement produits, plus une livraison courante delivered ou une entrée serveur delivered (ou cancelled avec previousStatus delivered), provenance admin/system et instant ISO strict valide. Tracking et cancelledAt seuls ne prouvent pas la livraison. Preuve absente : 409 referral_delivery_evidence_missing ; snapshot absent : 409 referral_reconciliation_not_applicable.

Active et drain opérationnels réutilisent prepareReferralTransition(event: delivery). Off refuse en 503 referral_program_disabled, configuration malformed en 503 referral_configuration_invalid. Cette branche ne prépare aucun plan fidélité/annulation/stock/promotion/facture ; elle ne produit aucun email, analytics, historique de statut ou updatedAt commande. Elle écrit uniquement la relation, le wallet parrain et les mouvements nécessaires, dans la même transaction avec toutes les lectures avant écritures. Une commande cancelled reste strictement inchangée. Les replays concurrents sont idempotents ; mauvaise commande qualifiante, paiement entièrement off, refund sous seuil ou inéligibilité ne créent aucun gain. Une correction ultérieure exploite les faits livraison alignés via le moteur existant. Le replay orderStatus=delivered sur une commande encore delivered est conservé.

## Validation et gates restants

### Livraison persistée pendant off

Si le paiement a déjà qualifié la relation en `pending`, une livraison enregistrée pendant `off` ne modifie ni la relation ni le wallet parrain. Après retour à un runtime opérationnel `active` ou `drain`, un admin peut rejouer explicitement `{ orderStatus: "delivered" }` sur cette même commande déjà payée et livrée. Ce rattrapage réutilise le ledger de livraison existant et sa compensation de régularisation, sans relire Auth ni keyring. Il conserve `previousStatus=delivered` et n’ajoute aucun statut, email, achat analytics, mouvement fidélité ou effet stock. Les replays et leur concurrence sont idempotents.

Le mode `off` reste inert. Une relation d’une autre commande, un paiement jamais qualifié parce qu’effectué pendant off, une annulation sous seuil ou une inéligibilité persistée ne gagnent aucun droit par ce replay. Les faits livraison peuvent servir à une correction administrative ultérieure. Les snapshots et la configuration restent strictement validés. Sans snapshot, ou pour une note, un tracking, un archivage, un masquage ou un événement payment-link sans intention de livraison, aucun rattrapage ni résolution de runtime Referral n’est ajouté. Aucun cron, backfill ou effet de lecture n’est prévu.

### Migration technique et déploiement futur

`scripts/migrateOrderCustomerEmailNormalization.ts` est DRY-RUN par défaut. Il parcourt `orders` et `referrals` par pages (200 documents par défaut), valide les schémas et états cohérents des relations, ne rapporte que des compteurs et prépare uniquement `customerEmailNormalized`. Aucune création de droit, code, relation, claim, wallet ou mouvement. Une vraie commande produits historiquement payée sans email exploitable bloque la certification ; les précommandes payées sont incluses. Un apply ferme d’abord un ancien certificat si des écarts ou anomalies sont constatés, utilise des préconditions sur les documents afin de refuser un écrasement concurrent, puis refait une passe exhaustive. `complete` est écrit en dernier seulement si les emails exploitables sont tous canoniques et aucune commande payée pertinente n’a d’email inexploitable, aucune relation ne porte une identité non résolue et aucune relation corrompue n’a été trouvée. Un replay conserve les commandes correctes et un certificat cohérent sans nouvelles écritures. Les scripts de migration doivent être exécutés séquentiellement.

CLI futur (ne pas exécuter en Production dans ce lot) :

```text
node --import tsx scripts/migrateOrderCustomerEmailNormalization.ts --project=verdanza-1f621
node --import tsx scripts/migrateOrderCustomerEmailNormalization.ts --project=verdanza-1f621 --apply --confirm=order-email-normalization-v5
```

Le CLI refuse les arguments inconnus, un autre projet de credentials ou un environnement émulateur. L’engine testable n’autorise l’émulateur qu’avec le projet demo et le couple localhost/port exacts du runner isolé ; les tests n’importent pas le CLI ni les credentials Production. Les tests couvrent dry-run sans écriture, apply local avec vérification, anomalies et idempotence, paiement ambigu après certification, refus de recertification, récupération après réparation et course paiement/apply avec ancienne précondition. Cette migration technique ne produit aucune rétroattribution commerciale.

La migration ferme également la certification face à un document payé ambigu ou corrompu sans email exploitable : une preuve de paiement sans identité email ne peut pas prouver l’absence d’historique pour un compte recréé. Les fixtures marquées restent exclues de cette preuve de paiement.

Ordre obligatoire pour un futur gate distinct :

1. Déployer ce code avec Referral toujours OFF.
2. Vérifier les invariants : nouvelles commandes normalisées et chaque paiement produits authentifié laisse une preuve durable ; unresolved invalide atomiquement un marker existant.
3. Avec autorisation distincte, lancer le dry-run Production.
4. Examiner les anomalies.
5. Avec autorisation distincte, réconcilier les preuves missing/unresolved, puis appliquer la migration V5 séparément. Normaliser l’email checkout ne remplace jamais l’identité Auth.
6. Vérifier exhaustivement le résultat.
7. Certifier l’historique avec le marqueur complet.
8. Tout futur paiement legacy avec email inexploitable ré-invalide automatiquement ce certificat, même déjà incomplet, sans bloquer le paiement métier. Une nouvelle migration refuse de recertifier tant que l’anomalie payée subsiste ; après réparation administrative du brut, un apply et une vérification exhaustive peuvent le compléter.
9. Envisager une activation Referral séparément autorisée uniquement si le certificat reste complete.

**Aucune des étapes 3 à 9 Production n’est exécutée dans ce cycle. Aucune migration Preview, aucun marqueur Production, aucune activation et aucun déploiement Firebase rules/index.** La recherche canonique est une égalité simple ; aucun composite supplémentaire n’est requis.

`npm run test:referral-backend` utilise l’émulateur Firestore local et fait partie de `npm run verify` en CI. Les suites cagnotte et règles restent obligatoires. Les règles et index Firestore de ce commit sont des candidats versionnés, sans déploiement. Aucune variable Production ni donnée Production n’est créée. La remise checkout, l’affichage client et l’activation commerciale appartiennent aux lots suivants.


### Identité non résolue au paiement plain et certificat V5

Une commande sans snapshot reste payable en runtime opérationnel, sans gain parrain. Si le claim courant échoue avec `referee_identity_unavailable`, `referee_email_unverified` ou `referral_identity_changed`, la relation consommée conserve ce motif et le certificat V5 existant est invalidé dans la même transaction : `incomplete`, révision incrémentée, motif `payment_identity_unresolved`, instant technique, aucune PII. Un marker absent n’est jamais créé par le paiement. L’absence de runtime opérationnel n’ajoute aucune lecture de relation pour ce contrôle.

Cette relation persistante bloque toute recertification, même si l’ancien email de checkout est valide et toutes les commandes sont normalisées. Le scan paginé read-only de `referrals` rapporte `scannedReferralRelations`, `unresolvedIdentityRelations` et `corruptReferralRelations`. Les relations incohérentes ferment également la certification. Aucune anomalie n’est effacée automatiquement ; un futur processus admin de réconciliation nécessite un lot distinct. Le motif `referee_email_claimed` reste distinct : le claim existant protège déjà cet email. Un claim courant créé ou déjà détenu par le même filleul laisse le marker inchangé.

Le certificat `order-email-normalization-v5` exige `verifiedReferralRelations` entier positif ou nul et `verifiedUnresolvedIdentityRelations: 0` et `verifiedLinkedRelationsWithPaidHistory: 0`, en plus des preuves commandes. Une migration apply crée/ferme le marker avant ses scans de vérification. Un paiement intervenant après le scan modifie sa version Firestore et fait échouer la précondition `lastUpdateTime` de la certification finale ; un replay sans écriture revérifie aussi la version. Si le paiement précède la création du marker, son anomalie persistée est détectée par le scan. Les tests émulateur couvrent ces deux ordres, les pannes Auth/keyring, les comptes non vérifiés/désactivés, le binding changé, le claim déjà protégé, le rollback et les invalidations concurrentes.

`orderStatusRoute` conserve désormais le statut et le code de toute `ReferralError`, y compris `referral_program_disabled` en 503 lorsque le snapshot précède le début du programme. Les conflits 409, le type séparé `ReferralConfigurationError` et le comportement des erreurs non typées sont préservés. Ces modifications ne changent pas les settlements refund/correction ni les calculs financiers.

## Preuve durable de paiement et réconciliation technique V5

Chaque vraie commande produits authentifiée qui passe à payée écrit atomiquement `referralPaymentIdentities/<orderId>`. Les précommandes sont incluses ; commandes anonymes et fixtures exclues. Le document porte uniquement `schemaVersion: 1`, `version: referral-payment-identity-v1`, `orderId`, `customerUid`, `recordedAtEpochMs` et soit `status: claimed/protected_by_existing_claim`, `claimId`, `keyVersion`, soit `status: unresolved` et une raison bornée. Aucun email, nom, téléphone, token, secret ou matériau HMAC. La collection et ses descendants sont deny-all client dans les règles candidates non déployées.

Sous active/drain opérationnel, Auth est relu pour le customerUid même sans relation. L’email courant vérifié et le compte actif font foi : l’email checkout A reste conservé sur la commande même si Auth expose B. Toutes les clés HMAC retenues et l’alias legacy sont vérifiés transactionnellement. Libre/même UID donne claimed et la migration paresseuse vers le claim actif. Un autre UID valide donne protected_by_existing_claim sans écrasement pour un paiement sans remise. Un nouveau UID avec B ne peut ensuite obtenir de lien. Le même plan d’identité alimente preuve, consommation d’un lien existant et ledger, sans double création du claim.

Auth indisponible, email non vérifié/compte désactivé, identité inexploitable ou keyring invalide ne bloquent pas le paiement sans remise : preuve unresolved (`auth_unavailable`, `referee_email_unverified`, `identity_unavailable`, `keyring_unavailable`) et invalidation du marker existant dans la même transaction. Off/absent ou configuration malformed plain produisent `unresolved/runtime_closed` sans Auth, keyring, relation ou claims. Aucun marker absent n’est créé. Cette maintenance n’accorde aucun droit et ne crée ni relation, sponsor, remise ou reward. Le snapshot remisé conserve ses refus d’identité et de configuration ; un abort ne laisse aucune écriture partielle. Sponsor seul inéligible : payment et preuve claimed confirmés sans gain.

V5 exige `verifiedPaymentIdentityEvidence` entier et trois compteurs problématiques à zéro : `verifiedMissingPaymentIdentityEvidence`, `verifiedUnresolvedPaymentIdentityEvidence`, `verifiedCorruptPaymentIdentityEvidence`. Chaque `hasHistoricalPaymentEvidence(order)` avec customerId doit avoir sa preuve. Claimed exige un claim valide du même UID, `referralId === customerUid`, keyVersion identique ; protected exige un claim valide d’un autre UID. Schéma, version, orderId/customerUid, status, timestamp, champs bornés et référence de claim sont contrôlés. Les anciennes commandes payées sans preuve sont MISSING, même avec customerEmailNormalized. V1/V2/V3/V4 ne sont jamais READY. Les validations des relations et linkedRelationsWithPaidHistory restent indépendantes. La normalisation seule ne répare pas une preuve unresolved.

`scripts/reconcileReferralPaymentIdentities.ts` est dry-run par défaut, sans fallback Production. Il exige le projet explicite exact verdanza-1f621, le credential du même projet et un keyring serveur valide. Apply exige `--apply --confirm=referral-payment-identity-reconciliation-v1`. Les tests invoquent seulement l’engine injecté : demo-verdanza-cagnotte et émulateur exact 127.0.0.1:18085. Aucun CLI migration/réconciliation n’est exécuté Production dans ce cycle, même dry-run.

Pour missing/unresolved, l’engine relit Auth hors transaction, puis relit atomiquement ordre, preuve et aliases. Il revérifie paiement historique, customerId inchangé et absence de fixture. Il crée/migre uniquement claim et preuve claimed/protected. Auth supprimé/indisponible/non vérifié laisse missing/unresolved, rapporté en compteurs sans PII ; keyring invalide ferme avant toute écriture. Les preuves sûres restent inchangées au replay. Aucun ordre, relation, sponsor, wallet, reward, remise ou certificat n’est modifié. Les courses claims/evidence sont sérialisées ; seule la migration V5 ultérieure peut certifier complete.

Les anciennes clés HMAC doivent rester disponibles tant qu’un claim dépendant d’une relation **ou d’une preuve de paiement**, même sans relation, en dépend. La migration paresseuse ne supprime aucun ancien claim ; retirer une clé exige un audit exhaustif distinct. Aucun secret, keyring, flag ni variable Production ajouté dans ce lot.


## Historique durable de paiement et tombstones V5

`referralPaymentIdentities/<orderId>` est créée seulement au paiement produits authentifié confirmé. Elle prouve durablement que son `customerUid` a déjà payé, même après suppression physique de `orders/<orderId>`. La suppression HTTP ou le cleanup des commandes non enrôlées ne cascade jamais ces preuves ni `referralEmailClaims`. Elles n'expirent pas. Un claim seul peut précéder tout paiement : il ne constitue donc jamais une preuve de paiement.

Le contrôle filleul interroge transactionnellement les preuves par égalité `customerUid`, avec limite 100 (index single-field standard, aucun composite ajouté). Shape safe (`claimed`/`protected_by_existing_claim`) ou unresolved = paiement antérieur positif ; aucun ordre, claim ou certificat n'est nécessaire pour ce fait. Même un ID égal à la commande courante est historique s'il existe déjà. Sans preuve positive, une preuve corrompue/saturation rend l'historique inconclusive. Une preuve positive commande ou identity gagne sur corruption et certificat absent/incomplet. Link refuse `referee_already_paid` ; un nouveau paiement remisé refuse `referral_discount_already_consumed`. L'éligibilité parrain payé ET livré continue de vérifier la vraie commande, sans utiliser les payment identities.

La certification V5 scanne toutes les payment identities indépendamment de orders, par pages. Chaque preuve est comptée une fois ; orders vérifie seulement présence/binding de sa preuve attendue. Les claims sont audités séparément pour certifier la sûreté d'identité : claimed exige propriétaire identique, protected propriétaire différent. Orphan safe + claim cohérent passe ; orphan unresolved/corrupt/claim manquant ou invalide bloque. `verifiedDetachedPaymentIdentityEvidence` compte les preuves sûres sans commande ; il est entier, non négatif et inférieur ou égal à `verifiedPaymentIdentityEvidence`, qui n'est plus limité au nombre de commandes encore présentes. Missing/unresolved/corrupt et les anciens blockers doivent rester zéro. V1/V2/V3/V4 sont NON READY. La suppression d'une commande ne nettoie jamais une anomalie unresolved.

Le reconciler pagine aussi les preuves sans commande. Une unresolved orphan structurellement valide fournit elle-même orderId/customerUid du paiement historique. Auth est relu hors transaction ; preuve, absence de commande et aliases sont relus atomiquement avant claim/evidence. UID changé, preuve disparue/corrompue ou commande réapparue ferme la tentative. Auth indisponible/supprimé laisse unresolved. Il ne recrée aucun ordre et ne touche aucun droit, relation, reward, remise, wallet ou marker. Dry-run par défaut et confirmation apply restent inchangés ; replay et concurrence sont idempotents. Seule la migration V5 ultérieure peut certifier.

Aucune migration/réconciliation Production, même dry-run, ni activation/configuration/infrastructure Production dans ce lot. Les tests de suppression, certification orphan et reconciliation utilisent seulement l'émulateur dédié et Auth mocké.
